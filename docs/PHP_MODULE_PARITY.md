Node keeps incidents in one global Redis zset, breaker state in an in-process `Map` and events in a log ring; all three are MySQL here, and each was a bug in the original: incident lists and access reviews are now scoped to the caller's organization (one tenant could read another's incidents), `REVOKE_TOKENS` revokes the refresh tokens of the reporting organization instead of every session on the platform, and breaker state survives the request. | Global Platform / observability + regions + CDN (`platform`) | Yes | Yes — 6 new tables | Yes | Yes | **Runtime validated.** All 15 endpoints ported: metrics, logs, traces, one trace, one span, AI observability, regions, the DR report, failover trigger/clear, CDN config, cache rules (PUT), purge and sign-url, and the combined overview. Node keeps all of this in process memory — metric Maps, a 2000-entry log ring, a 500-span ring, four module-level variables for failover, and two arrays for CDN rules and purges — so a faithful port would have reported zero spans, zero metrics and no failover state on every request. It is MySQL here: `platform_metric_counters` / `platform_metric_histograms` (one row per name/tag/minute, upserted, so a busy route costs one row a minute rather than one a request), `platform_spans`, `platform_state`, `platform_cdn_rules` and `platform_cdn_purges`. Every request opens a root span and records `http.request.count` + `http.request.duration_ms` under the same names Node's middleware uses, so the admin dashboard's panels find their series without a special case; W3C `traceparent` is honoured inbound and echoed outbound. Logs are **not** given their own table — the durable records this build keeps are `audit_events`, failed spans and failed AI requests, so `/platform/logs` merges those three and labels every row with its `source`, rather than inventing a ring buffer to look like Node's. Two numbers Node invents are reported as null: `replicationLagMs: 42` (a literal in `getDisasterRecoveryReport()` — a single-database deployment has no replica to measure) and `popCount: 42` / `cacheHitRate: 0.87` (labelled “simulated” in its own source) / `bandwidthGb: 12.4` (literals in `getCdnConfig()`). A purge with no provider configured is recorded as `skipped` with a reason instead of Node's 150 ms sleep followed by “complete”, and `sign-url` is a real HMAC-SHA256 over `VP_AUTH_SECRET` with `cdn_exp` then `cdn_sig`, so it is verifiable rather than decorative. | Module Center / signed packages (`moduleCenter`) | Yes | Yes — 4 new tables | Yes | Yes | **Runtime validated.** All 13 super-admin routes ported: dashboard, module list/detail, upload intake (GET + POST), operations, verify, sandbox-test, approve, install, and enable / disable / restart / health-check / rollback / remove. The four Prisma tables become `platform_modules`, `platform_module_releases`, `platform_module_uploads` and `platform_module_operations`, and artifacts are stored under `application/storage/module-packages/` in the same quarantine / verified buckets Node uses. The ZIP reader is dependency-free (central-directory parsing plus `gzinflate`, so no ext-zip is required on the host) and the manifest schema is ported field by field, including the cross-field rules (a disabled backend may not declare routes, duplicate routes and page paths are rejected, rollback-supported migrations require rollback files). Two boundaries are inherited rather than invented: verification **fails closed** (a detached publisher signature and a reachable ClamAV are both required, exactly as in Node), and anything that would execute uploaded code is delegated to the isolated Module Runner over an HMAC-signed call — with no runner configured those actions record the attempt and return `NOT_CONFIGURED`, leaving the package inactive, which is the same result the Node service returns. The one real difference: Node verifies Ed25519 signatures with its own crypto, while PHP verifies Ed25519 through ext-sodium when it is loaded and otherwise reports `SIGNATURE_UNVERIFIABLE` rather than passing; RSA/ECDSA publisher keys verify on every host, and the parity spec signs with RSA for that reason. Validated 124/124 parity on a fresh install seeded from `database/production.sql`, plus 11 web tests covering the client contract (the multipart `package` field and a fresh 12..180 character idempotency key per action) |
| Module Runtime / module gateway (`moduleRuntime`) | Yes | No — reuses the Module Center tables | Yes | Yes | **Runtime validated.** All four routes ported: `/health` (registration count for the caller's role), `/modules` and `/registrations` (the same role-filtered surface), and the `ANY /:moduleKey/*` gateway. The gateway enforces the manifest's own contract in order — the module must be ACTIVE *and* enabled, the caller's role must be in `accessRoles`, the method and path must match a declared `backend.routes` entry (`:param` and a trailing `*` are matched the way Node matches them), and the caller must hold the permission that route names, which must also exist in the platform catalogue so a manifest cannot invent one. Only then does it dial the registered `serviceUrl` with the HMAC-signed context header (`x-windels-module-context` / `-timestamp` / `-signature`, signed over `<timestamp>.<context>.<method>.<path>`), a response-size cap and a timeout. Two deliberate differences: registrations also strip `instanceId` and `imageDigest` (Node strips only `serviceUrl`) because they are internal deployment coordinates a browser has no use for, and an unreachable module backend returns `502 MODULE_RUNTIME_UNREACHABLE` with the transport error instead of Node's unhandled 500.
