# Blockonomics API, Setup, Deployment, and Operations Guide

**Implementation stages covered:** 1–14 of 15

**Code status:** implemented and repository-tested

**Production status:** **NOT PRODUCTION COMPLETE** — real PostgreSQL and
Blockonomics Test Mode evidence is still required in Stage 15.

## 1. Capability and trust boundaries

Blockonomics is provider ID `blockonomics`. It is additive to Stripe, PayPal,
Paystack, Flutterwave, WMPC Gift Card, and the existing generic `crypto` safety
gate.

Provider capability is deliberately narrow:

| Asset | Network | Provider callback finality | Smallest units |
|---|---|---:|---:|
| BTC | Bitcoin | Blockonomics status `2` | 8 decimals / satoshis |
| USDT | Ethereum ERC-20 only | Blockonomics status `2` | 6 decimals |

TRON, BNB Chain, BCH checkout, arbitrary wallet credit, and automatically
recurring crypto charges are not advertised or implemented. The generic
`crypto` provider remains blocked.

The browser and AI tools can display backend facts. They cannot confirm,
complete, reconcile, settle, credit, debit, or refund payment. A payment reaches
`completed` only after backend provider verification and the existing atomic
billing transaction.

## 2. Runtime prerequisites

- Node.js and pnpm versions from the root `package.json`, or the supported Docker
  Compose deployment.
- PostgreSQL with all committed Prisma migrations applied.
- Redis with persistence for rate limits, existing fiat history, and the
  reconciliation distributed lock.
- `WINDELS_ENCRYPTION_KEY`: exactly 64 hexadecimal characters.
- HTTPS public API origin in `WINDELS_PUBLIC_API_ORIGIN`.
- A Blockonomics account/store configured for merchant receiving.
- A cryptographically random callback secret of at least 32 characters.

Generate suitable secrets without putting them in shell history or source
control. One option on a secured administrator workstation is:

```bash
openssl rand -hex 32
```

## 3. Blockonomics store configuration

In Blockonomics:

1. Configure the merchant store/wallet for BTC and/or USDT on Ethereum ERC-20.
2. Enable Blockonomics Test Mode for qualification.
3. Configure the callback URL:

```text
https://YOUR_API_DOMAIN/api/v1/payments/blockonomics/webhook?secret=YOUR_32_PLUS_CHARACTER_SECRET
```

4. Use the same callback secret in WINDELS.
5. Set WINDELS `matchCallback` / `BLOCKONOMICS_MATCH_CALLBACK` to the host or
   matcher used by the corresponding Blockonomics store callback.

Blockonomics appends `addr`, `status`, `value`, `txid`, and optional callback
parameters. Because the configured URL already contains `secret`, subsequent
parameters must be appended with `&`. Verify the exact URL generated by the
provider during Test Mode.

Do not place the callback secret in client code, screenshots, tickets, or test
evidence. WINDELS redacts sensitive query values from access logs, traces, and
structured HTTP logs, but the provider configuration and operator workflow must
also protect it.

## 4. Configuration methods

### 4.1 Recommended: Super Admin encrypted configuration

1. Sign in as `super_admin`.
2. Open `/platform/blockonomics`.
3. Enter the provider API key and callback secret.
4. Select BTC and/or USDT ERC-20.
5. Set Test Mode, callback match host, and quote timer.
6. Save while the provider is disabled.
7. Run **Check provider health**.
8. Enable only for controlled Test Mode validation.

Secret fields are write-only. A blank field retains the encrypted database
value. The API never returns decrypted credentials.

### 4.2 Environment bootstrap

Environment values are a bootstrap path. The first Super Admin mutation adopts
them into encrypted PostgreSQL storage; the database row then becomes
exclusive source of truth.

```dotenv
BLOCKONOMICS_ENABLED=false
BLOCKONOMICS_API_KEY=
BLOCKONOMICS_CALLBACK_SECRET=
BLOCKONOMICS_MATCH_CALLBACK=payments.example.com
BLOCKONOMICS_SUPPORTED_ASSETS=BTC,USDT
BLOCKONOMICS_QUOTE_EXPIRY_MINUTES=15
BLOCKONOMICS_TEST_MODE=true
BLOCKONOMICS_RECONCILIATION_ENABLED=true
BLOCKONOMICS_RECONCILIATION_INTERVAL_MINUTES=15
```

Constraints:

- callback secret: at least 32 characters;
- assets: `BTC`, `USDT`, or both;
- quote timer: 5–60 minutes;
- reconciliation interval: 5–1440 minutes;
- final confirmations: fixed at provider status `2`.

WINDELS Test Mode controls the USDT monitor `testnet` flag and UI posture. It
does not enable Test Mode in the Blockonomics store. Configure both.

## 5. Database deployment

The Blockonomics foundation migration is:

```text
apps/api/prisma/migrations/20260817120000_blockonomics_payment_foundation/migration.sql
```

It adds durable provider configuration, payment records, callback inbox,
invoice allocations, generalized existing-ledger fields, foreign keys, indexes,
and RLS policies.

Docker deployment applies migrations in the one-shot bootstrap container before
the API becomes healthy. For a managed target environment, run the repository's
normal migration command with the schema-owner connection:

```bash
pnpm db:generate
pnpm db:migrate
node scripts/validate-migrations.mjs
```

Then verify the API uses a non-superuser database role so RLS is enforceable.
Do not validate RLS while connected as a PostgreSQL superuser and call that
production evidence.

## 6. Authenticated customer/payment API

All endpoints below require JWT authentication and organization context except
the provider callback.

### 6.1 Provider registry

```http
GET /api/v1/payments/providers
```

The `blockonomics` entry reports configured/enabled status, Test Mode, supported
fiat currencies, networks, and configured BTC/USDT assets. It contains no
secret.

### 6.2 Create through universal checkout

```http
POST /api/v1/payments/checkout
Content-Type: application/json
Authorization: Bearer <JWT>

{
  "provider": "blockonomics",
  "amount": 60.00,
  "currency": "USD",
  "cryptoCurrency": "BTC",
  "invoiceId": "<organization-invoice-id>",
  "description": "Payment for invoice"
}
```

A provider-specific alias is also available:

```http
POST /api/v1/payments/blockonomics/create
```

For an invoice, `amount` must equal the exact remaining invoice amount after all
applied allocations, including WMPC Gift Card. The server persists `created`
before requesting a live `/price` and `/new_address` response. Provider failure
returns an error and never returns a fabricated address.

Safe response fields include:

- WINDELS payment ID and reference;
- fiat amount/currency and invoice ID;
- BTC or USDT/ERC-20 asset/network;
- provider address;
- exact expected smallest units and display amount;
- quote source/time/expiry;
- confirmations and backend status;
- safe payment instructions.

### 6.3 Read status

```http
GET /api/v1/payments/blockonomics/payments/<payment-id>
```

Status is organization-scoped. Client polling is informational and does not
advance payment state.

### 6.4 Submit USDT transaction hash for monitoring

```http
POST /api/v1/payments/blockonomics/payments/<payment-id>/monitor
Content-Type: application/json
Authorization: Bearer <JWT>

{
  "txhash": "0x<64 hexadecimal characters>"
}
```

Only the original payment requester may submit the hash. The operation calls
official `/monitor_tx`, writes an audit record, and may report detected or
confirming. It never completes payment; callback or reconciliation must
independently verify final history.

### 6.5 Unified organization history and detail

```http
GET /api/v1/payments/transactions?provider=blockonomics&status=completed&limit=50
GET /api/v1/payments/transactions/<payment-id>
```

The existing history merges PostgreSQL Blockonomics records with the existing
fiat-provider Redis ledger, sorts newest-first, and retains organization
isolation. A completed Blockonomics detail may contain safe provider transaction
and WINDELS receipt evidence.

## 7. Public provider callback

```http
GET /api/v1/payments/blockonomics/webhook
```

Validated query fields:

| Field | Required | Meaning |
|---|---:|---|
| `secret` | yes | configured 32+ character callback secret |
| `addr` | yes | provider payment address |
| `crypto` | no | absent/BTC defaults to `BTC`; otherwise `USDT` |
| `status` | yes | `0`, `1`, or final `2` |
| `value` | yes | positive integer BTC satoshis or USDT base units |
| `txid` | yes | provider transaction ID/hash |
| `rbf` | no | provider replace-by-fee flag |

Processing rules:

1. rate limit by callback source IP;
2. validate schema and compare secret in constant time;
3. claim durable unique event key
   `blockonomics:{crypto}:{addr}:{txid}:{status}:{value}`;
4. match provider/address/asset/amount against durable local state;
5. record status 0/1 without billing settlement;
6. for status 2, query authenticated provider history;
7. settle only exact, timely, independently verified evidence;
8. return success only after durable processing.

Unknown payments are durably ignored. Underpayment, overpayment, duplicate
transaction, ambiguity, wrong provider evidence, and late payment enter review.
Transient failures return non-2xx so Blockonomics can retry.

## 8. Super Admin API

All routes require JWT `super_admin` and use the admin rate limit.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/admin/payments/blockonomics/config` | redacted public config |
| PUT | `/api/v1/admin/payments/blockonomics/config` | rotate write-only secrets and settings |
| PATCH | `/api/v1/admin/payments/blockonomics/enabled` | enable/disable |
| POST | `/api/v1/admin/payments/blockonomics/health` | authenticated read-only provider health |
| GET | `/api/v1/admin/payments/blockonomics/dashboard` | payments, errors, callbacks, reconciliation posture |
| POST | `/api/v1/admin/payments/blockonomics/reconcile` | manual authenticated history comparison |

Configuration update body:

```json
{
  "apiKey": "optional-new-provider-key",
  "callbackSecret": "optional-new-secret-at-least-32-characters",
  "settings": {
    "enabled": false,
    "testMode": true,
    "matchCallback": "payments.example.com",
    "supportedAssets": ["BTC", "USDT"],
    "quoteExpiryMinutes": 15,
    "requiredConfirmations": 2
  }
}
```

Manual reconciliation body:

```json
{ "timeframe": "1M" }
```

Allowed timeframes are `1W`, `2W`, `1M`, `3M`, `6M`, and `1Y`.

There is intentionally no admin route to force-complete, credit, debit, or
refund Blockonomics payments.

## 9. Payment lifecycle

| WINDELS status | Meaning | Financial effect |
|---|---|---|
| `created` | durable local record exists; provider setup in progress | none |
| `pending` | quote/address returned | none |
| `detected` | provider status 0 | none |
| `confirming` | provider status 1 or monitored hash | none |
| `confirmed` | authenticated final provider evidence matched | eligible for atomic settlement only |
| `completed` | invoice allocation, ledger, invoice/subscription, receipt, and audit committed | settled |
| `expired` | quote elapsed with no provider payment found | none |
| `under_review` | mismatch, ambiguity, late payment, missing target, or duplicate | no automatic settlement |
| `failed` / `cancelled` | terminal failure/cancel | none |
| `refunded` | reserved lifecycle state; no Blockonomics refund API is implemented | no browser/AI action |

BTC addresses do not expire merely because the quote timer elapsed. A payment
arriving after the quote requires backend review. Do not tell a customer the
browser timer invalidated an on-chain address.

## 10. WMPC Gift Card split tender

1. Apply the WMPC Gift Card to the invoice in the same currency.
2. WINDELS records the gift-card allocation and existing-ledger journal.
3. Read invoice `remainingCents` from billing overview.
4. Create Blockonomics for exactly that remainder.
5. Keep the gift-card allocation if quote creation or expiry occurs.
6. Mark invoice paid only when applied allocations exactly equal invoice total.

Gift-card and provider entries use the existing billing ledger. No second
wallet or ledger is created.

## 11. Subscriptions

Blockonomics is not an automatically recurring mandate. Each renewal requires a
new invoice and a new customer-authorized payment. Subscription activation or
restoration occurs only after the associated invoice is fully settled. Do not
store an address and imply future automatic collection.

## 12. Reconciliation operations

Scheduled reconciliation defaults to every 15 minutes while configured and
enabled. A Redis distributed lock prevents overlapping runs across replicas.
Each asset fetch is bounded by official provider history to 200 rows.

Reconciliation can:

- match exact provider evidence;
- recover eligible pending/expired records through the same atomic settlement;
- identify missing, orphan, duplicate, ambiguous, wrong amount/address/asset,
  late, and settlement-failure cases; and
- write issue/run audit evidence.

It cannot silently reverse a completed payment or adjust a balance. Choose a
provider timeframe appropriate for transaction volume; high-volume stores may
need more frequent runs.

## 13. AI access

The existing AI tool registry contains only:

- `get_blockonomics_payment_status`;
- `get_blockonomics_payment_instructions`.

They require organization/user context, return backend facts, reconstruct exact
crypto amount from smallest units, and audit reads. No AI payment mutation tool
exists.

## 14. Monitoring and troubleshooting

### Provider remains `not_configured`

- verify API key is non-empty;
- verify callback secret is at least 32 characters;
- verify the AES primary key/keyring can decrypt the DB envelope;
- remember that a DB configuration row overrides environment values.

### Provider is configured but disabled

Enable only from Super Admin after health and Test Mode qualification. A normal
organization admin cannot enable it.

### Health is unhealthy

- inspect sanitized `lastError` in `/platform/blockonomics`;
- verify API key, outbound HTTPS/DNS, store access, and provider availability;
- do not test health by allocating an address.

### Callback does not arrive

- verify public HTTPS and callback URL/secret;
- verify callback query uses `&` after the configured `secret`;
- check callback processing counts/errors;
- inspect reverse proxy and firewall;
- run manual reconciliation;
- never simulate a successful callback in production records.

### Payment remains confirming

- confirm two-or-more provider confirmations;
- for USDT, verify Ethereum ERC-20 and transaction hash;
- refresh backend status rather than trusting browser state;
- run reconciliation and inspect review issues.

### Payment is under review

Do not force completion. Compare asset, address, exact base units, txid,
timestamp/quote, invoice remaining balance, duplicate assignments, and provider
history. Preserve all existing allocations and audit evidence.

## 15. Stage 15 target-runtime acceptance checklist

Capture evidence for every item without recording secrets:

### PostgreSQL

- [ ] migrations apply from a clean database;
- [ ] migration validator passes;
- [ ] API role is not a PostgreSQL superuser;
- [ ] RLS blocks cross-tenant payment/history reads;
- [ ] callback and settlement transactions commit and roll back correctly;
- [ ] concurrent duplicate callbacks/settlements remain idempotent;
- [ ] WMPC plus Blockonomics allocation conservation holds on real transactions.

### Blockonomics Test Mode

- [ ] real authenticated health succeeds;
- [ ] real BTC `/price` and `/new_address` responses persist;
- [ ] real USDT `/price`, address, and `/monitor_tx` responses persist;
- [ ] actual callback status 0, 1, and 2 progress correctly;
- [ ] duplicate callback delivery produces no duplicate financial effect;
- [ ] wrong secret is rejected and absent from logs/traces;
- [ ] under/over/late/unknown cases enter review;
- [ ] `/v2/payments` reconciliation matches exact provider history;
- [ ] an orphan/missing test case is visible to Super Admin;
- [ ] a fully paid invoice produces one allocation, journal, receipt, audit, and
      subscription activation;
- [ ] history and receipt are visible only in the owning organization.

### Browser and AI

- [ ] BTC and USDT selector honors server configuration;
- [ ] QR is scanned by representative wallets on the correct network;
- [ ] quote timer never marks payment complete;
- [ ] USDT hash submission only begins backend monitoring;
- [ ] AI tools return status/instructions and cannot mutate payment;
- [ ] normal admin cannot access Super Admin provider controls.

### Live-mode change control

- [ ] Test Mode evidence reviewed by payment/security owners;
- [ ] production credentials rotated into encrypted DB storage;
- [ ] callback secret and URL changed from test values;
- [ ] backups and rollback tested;
- [ ] reconciliation/on-call runbook assigned;
- [ ] provider enabled under approved change record;
- [ ] first low-value live payment observed end to end.

Only after these items pass in the target environment may a separate production
acceptance record consider the integration production-complete.
