## 1. Objective

Session 70 shipped the Global Command Center as two thin pieces: an executive
rollup computed from the real `Agent`, `Workflow`, `Task`, `Conversation`,
`AiRequest` and `Alert` tables, and a "directives" list backed by the generic
`tenantStore` helper. The audit classified the module `PARTIAL`, and correctly
so:

- `packages/shared/src/command.ts` had **types but no Zod contracts** — the
  route file declared its own local schema;
- there were only four endpoints, and four of the dashboard's arrays —
  `regions`, `incidents`, `briefings`, `strategicInitiatives` — were
  **hardcoded `[]`**, so the "regional status", "incident command" and
  "executive briefings" panels of the PlatformPage tab could never render
  anything;
- `mttrMinutes` was a hardcoded `0` with a comment admitting the paired
  open/close timestamps were not recorded anywhere;
- directives were opaque `{ data: … }` envelopes with no issuer, no transition
  author and no note, so nothing could be rolled up from them;
- the web client was a single `dashboard()` call, the module had no page of its
  own, and the tab rendered every count as `value / 1000 + "K"` — so a real
  count of 7 active users displayed as `0K`;
- the only coverage was one e2e assertion that the empty arrays were arrays.

Session 111 completes the module as a real **operations register** without
inventing a single unit of intelligence:

1. shared `Cmd*` incident/region/briefing/initiative/directive types and Zod
   contracts;
2. an organization-scoped service with fail-closed reads and CSPRNG ids;
3. an idempotent in-place migration of the Session 70 directive envelopes;
4. a deterministic rollup whose MTTR is **measured**, whose regions can be
   honestly `unreported` and whose empty states are empty;
5. a complete route surface with admin-guarded mutations;
6. a typed client plus a dedicated `/app/command` console;
7. seventeen service/contract tests, and display-honesty fixes in the existing
   PlatformPage tab.

## 2. Domain model

| Record | Purpose | Honesty rule |
|---|---|---|
| `CmdIncident` | a declared operational incident on a service, optionally in a registered region | born `open`; a **named human** acknowledges and a **named human** resolves it with a mandatory note. `timeToResolveMinutes` is measured from the stored `openedAt`/`resolvedAt` pair and is `null` while open. Nothing auto-resolves |
| `CmdRegion` | the operator's declared footprint | `servicesUp`, `latencyMs` and `activeUsers` stay `null` until an operator files a status report. Health is `unreported` until then — never optimistically `healthy`. The platform probes nothing |
| `CmdBriefing` | an executive briefing | authored by a human, or explicitly `origin: "ai_assisted"` with `aiAssisted: true`, counted separately and badged advisory in every surface |
| `CmdInitiative` | a strategic initiative | `progressPct` is the owner's own number, always stamped `progressKind: "self_reported"`; it is never derived from tasks, commits or workflow runs |
| `CmdDirective` | the Session 70 directive log, completed | records the issuer, the transition author and an optional note; a resolved or cancelled directive cannot be moved again (`409`) |
| `CmdOperationsRollup` | deterministic projection over the five record types | counts, shares and measured durations only — no forecast, no score, no verdict |

### What is deliberately *not* implemented

`globalRevenueMtd` and `humanOverrides24h` stay `0`: there is no revenue ledger
or override log behind the command centre, and a plausible number there would
imply subsystems that do not exist. Regional latency and active users are not
synthesised — they are `null` unless an operator typed them in. No briefing is
generated by the platform.

## 3. Storage and isolation

```
cmd:meta:i:<org>:center             register bootstrap marker
cmd:incident:i:<org>:<id>           cmd:incident:idx:<org>
cmd:region:i:<org>:<id>             cmd:region:idx:<org>
cmd:briefing:i:<org>:<id>           cmd:briefing:idx:<org>
cmd:initiative:i:<org>:<id>         cmd:initiative:idx:<org>
cmd:dir:i:<org>:<id>                cmd:dir:idx:<org>
```

- Every read re-checks the stored `organizationId` and returns `null` when it
  does not match the requested slot (fail-closed) — a record planted under
  another organization's key is invisible, not merely unlisted.
- Ids are `randomUUID()`-derived: `cmd_inc_…`, `cmd_reg_…`, `cmd_brf_…`,
  `cmd_ini_…`, and directives keep the Session 70 `cmd-…` prefix. There is no
  `Math.random` anywhere in the module, read path or write path.
- The directive key shape is the one Session 70's
  `tenantStore({ prefix: "cmd:dir" })` produced, so historical rows are read,
  normalized and rewritten in place on first access. Re-running the migration
  is a no-op: `data` envelopes are unwrapped exactly once, the index keeps a
  single entry per record, and nothing is duplicated. A legacy record never
  captured who moved its status, so `statusChangedBy`/`statusNote` migrate as
  `null` rather than being attributed to the issuer.
- The six namespaces are registered in `TI_NAMESPACE_CATALOG`
  (`tenantIsolation.service.ts`) so the Session 89 live audit covers them.
- Kernel events (`command.incident_declared`, `command.incident_acknowledged`,
  `command.incident_resolved`, `command.region_status_reported`,
  `command.directive_issued`) are dispatched best-effort from write paths only;
  a telemetry failure never fails a write, and no event is emitted from a read.

## 4. Rollup mathematics (deterministic)

| Field | Definition |
|---|---|
| `openIncidents` | incidents whose status is not `resolved` |
| `unacknowledgedIncidents` | incidents still in `open` — declared but nobody has taken ownership |
| `incidentsBySeverity` / `unresolvedBySeverity` | partitions of the register by declared severity |
| `meanTimeToResolveMinutes` | `round(Σ measured minutes ÷ resolved incidents)`, **`null`** when nothing has been resolved — never `0`, which would read as "instant recovery" |
| `mttrSampleSize` / `mttrKind` | how many resolved incidents the mean came from, and `measured` vs `none` |
| `regionsUnreported` | regions with no operator status report — a measured gap, not a guess |
| `reportedServicesUp` | sum over reported regions, `null` when no region has been reported |
| `avgReportedProgressPct` | mean of the owners' own numbers, `null` when there are no initiatives |
| `progressKind` | `self_reported_average` or `none` |
| `humanBriefings` / `aiAssistedBriefings` | partition of the briefing log by origin |
| `lastIncidentOpenedAt` / `lastDirectiveIssuedAt` | max stored timestamp, `null` when empty |

Region health is derived by a stated rule, and every region carries the
sentence that produced it in `healthBasis`:

1. no status report → `unreported`;
2. `servicesTotal > 0` and `servicesUp === 0` → `down`;
3. `servicesUp < servicesTotal` → `degraded`;
4. all services up but unresolved incidents in the region → `degraded`;
5. otherwise → `healthy`.

The rollup contains **no wall-clock arithmetic and no generated timestamp**, so
two consecutive reads of an unchanged organization are byte-identical — pinned
by a `JSON.stringify` equality test.

## 5. API surface (`/api/v1/command`, authenticated)

| Method | Path | RBAC | Purpose |
|---|---|---|---|
| GET | `/dashboard/rollup` | member | Session 70 rollup + `directives` + `operations` (backwards-compatible superset) |
| GET | `/operations` | member | deterministic operations rollup |
| GET/POST | `/incidents` | member / admin | list (filter by status/severity/region), declare |
| GET/PATCH/DELETE | `/incidents/:id` | member / admin | detail, edit metadata, delete |
| POST | `/incidents/:id/updates` | admin | append a human timeline note, optionally moving to `acknowledged`/`mitigating` |
| POST | `/incidents/:id/acknowledge` | admin | a named human takes ownership |
| POST | `/incidents/:id/resolve` | admin | human resolution with a mandatory note |
| GET/POST | `/regions` | member / admin | list, register |
| GET/PATCH/DELETE | `/regions/:id` | member / admin | detail, edit, delete |
| POST | `/regions/:id/status` | admin | operator status report |
| GET/POST | `/briefings` | member / admin | list (filter by priority/category/origin), publish |
| GET/DELETE | `/briefings/:id` | member / admin | detail, delete |
| GET/POST | `/initiatives` | member / admin | list, add |
| GET/PATCH/DELETE | `/initiatives/:id` | member / admin | detail, report progress, delete |
| GET/POST | `/directives` | member / admin | list, issue |
| GET | `/directives/:id` | member | detail |
| PATCH | `/directives/:id/status` | admin | acknowledge / resolve / cancel |

Twenty-nine endpoints, up from four. Guard rails at the boundary:

- an incident naming a region that is not registered in the organization is a
  `404`, not a silently-stored dangling reference;
- deleting a region that still has unresolved incidents is a `409` naming the
  count, rather than dropping live incidents off the regional board;
- reporting more services up than the region declares is a `400` — clamping
  would quietly turn a data-entry error into a healthy-looking region;
- re-acknowledging, re-resolving or re-transitioning is a `409`.

## 6. Session 70 dashboard, now backed by records

`CommandService.dashboard()` keeps its Session 70 shape and fills the four
previously-empty arrays from the register:

- `regions` ← declared regions, with `servicesUp`/`latencyMs`/`activeUsers`
  passed through as `null` when unreported (the `RegionalStatus` contract was
  widened accordingly, and `health` gained `"unreported"`);
- `incidents` ← the incident register (the legacy `status` union gained
  `"acknowledged"`);
- `briefings` ← the briefing log, with AI-assisted summaries prefixed
  `[AI-assisted — advisory]` so the legacy shape stays labelled;
- `strategicInitiatives` ← initiatives, with `due` allowed to be `null` when the
  owner committed to no date;
- `mttrMinutes` ← the measured mean; `operations.mttrKind === "none"` marks a
  `0` that has no sample behind it;
- `incidentsOpen`/`incidentsCritical` sum two real sources — the platform
  `Alert` table (Session 70) and the incident register (Session 111);
  `operations` exposes the register's half on its own.

## 7. UI

`/app/command` (sidebar: "Global Command Center") is the dedicated console:

- unresolved/critical/unacknowledged incident counts, measured MTTR (rendered
  `—` with "no incident has been resolved yet" when there is no sample),
  declared regions with the unreported/degraded/down split, and the average
  **self-reported** initiative progress;
- incident command with the human timeline, acknowledge and resolve controls
  that refuse to submit without a note;
- regional posture showing each region's `healthBasis` verbatim, "never
  reported" instead of zeros, and an inline status-report form;
- briefings with an "AI-assisted (advisory)" badge, initiatives labelled
  "% self-reported", and the directive log with issuer and transition author;
- administrator-only mutations, explicit read-only state otherwise.

The existing PlatformPage "Command Center" tab stays. Three display bugs in it
were corrected as part of this session: active users and AI requests were
divided by 1000 and suffixed `K`/`k` (so every real count below a thousand read
as `0K`); MTTR rendered a hardcoded `0m` as a real measurement and now shows
`—` unless `mttrKind === "measured"`; and regional rows printed `null` latency
and user counts as numbers instead of omitting them.
