**Stage:** 9 of 15

## Delivered

### Unified existing history API

- Extended the existing organization-scoped
  `GET /api/v1/payments/transactions` endpoint to merge:
  - durable PostgreSQL `PaymentRecord` rows for Blockonomics; and
  - the pre-existing Redis transaction ledger for Stripe, PayPal, Paystack, and
    Flutterwave.
- Did not copy Blockonomics records into Redis and did not migrate or replace
  the legacy provider ledger.
- Applies provider and status filters to both sources, de-duplicates by provider
  and transaction ID, orders the merged result newest-first, and preserves the
  existing bounded limit.
- A Blockonomics-only query bypasses the Redis ledger, while non-Blockonomics
  provider queries do not require a Blockonomics history read.
- Extended the existing transaction-detail endpoint to resolve durable
  Blockonomics records before the legacy ledger.
- Both list and detail queries retain organization predicates. Cross-tenant IDs
  return no record.

### Safe details and receipts

- Added safe transaction-detail fields for provider transaction ID and the
  receipt generated by atomic Stage 6 settlement.
- Receipt data contains only receipt number, issue time, and invoice reference.
- Blockonomics serialization continues to expose only safe checkout evidence;
  encrypted API keys, callback secrets, provider configuration, and arbitrary
  stored metadata are not returned.
- Added regression coverage proving stored secret-like metadata is absent from
  user-facing details.

### Existing payment-history UI

- Renamed the existing ledger section to Organization Payment History and made
  its mixed durable/legacy source explicit.
- Added provider and status filters without introducing a second history page.
- Added backend-refreshed payment detail and receipt inspection in the existing
  modal architecture.
- Blockonomics details show exact expected crypto units, asset/network,
  confirmations, address, quote expiry, reconciliation state, invoice,
  provider transaction ID, and completion time.
- A WINDELS receipt is shown only when backend verification and atomic billing
  settlement generated one. The UI cannot fabricate or mark a receipt paid.
- Detail inspection is read-only and cannot confirm, complete, refund, cancel,
  credit, or otherwise mutate a payment.
