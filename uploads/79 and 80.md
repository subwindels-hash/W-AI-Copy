# WINDELS AI OS — CLAUDE.md (Sessions 79–80)

This file covers two additive updates, in build order. Nothing in Sessions 1–78 is
removed or modified by either session — both specs open with an explicit
"do not remove or modify any existing payment/wallet/billing/commerce functionality"
instruction. Both sessions reuse existing platform infrastructure — Billing &
Subscription Platform, Wallet System, Payment Gateway Framework, Marketplace, AI
Marketplace, Creator Economy, Enterprise Commerce Platform, Workflow Engine,
Security Framework, Governance Kernel, Audit System, Analytics Platform, and the
existing auth/org/permissions infrastructure — rather than re-implementing any of it.

**Build order matters here more than in prior sessions:** Session 80 (Global
Multi-Currency) explicitly lists "WMPC Gift Card" as one of the payment methods it
localizes, and its own spec header lists "WMPC Gift Card Platform" as a system it
extends. Session 79 must land first.

**Why this shape, across both sessions:**
- Two packages, because gift-card lifecycle/redemption is a distinct domain from currency
  detection/exchange-rate/localization — but `global-currency/payment-localization` explicitly
  imports and adapts `wmpc-gift-cards/core/GiftCardPaymentMethod` rather than re-describing gift
  card behavior, matching Session 80's own spec listing WMPC Gift Card as something it extends.
- `GiftCardPaymentMethod.ts` and every other payment surface **register into** the existing
  Payment Gateway Framework — neither session creates a second gateway or a second wallet.
- `LocalizationContext.ts` is the one place locale/currency/tax-region state lives; every pricing
  display in the dashboard reads from it instead of computing its own currency logic — this is the
  direct implementation of "do not create duplicate payment systems" applied to localization
  specifically, since duplicated locale logic is the most common way multi-currency features drift
  out of sync across a large app.
- AI agents in both packages (`SpendingAnalysisAgent`, `ExchangeRateTrendAgent`, etc.) extend
  `ExpertAgent` from Session 77's `experts-platform`, continuing the platform-wide agent contract
  established there and reused again in Session 78.

# SESSION 79 — WMPC Gift Card Payment Platform

## 79.1 Database Schema Additions

New tables only, foreign-keyed into existing `organizations.id`, `users.id`, `teams.id`,
and the existing payment-method/transaction tables.

`gift_cards`, `gift_card_types`, `gift_card_transactions`, `gift_card_redemptions`,
`gift_card_pins`, `gift_card_recipients`, `gift_card_delivery_schedule`,
`gift_card_enterprise_batches`, `gift_card_department_budgets`, `gift_card_loyalty_programs`,
`gift_card_fraud_flags`

## 79.2 Build Steps

1. **`GiftCard` core model + lifecycle** — card types (physical, digital, virtual, one-time,
   reloadable, promotional, enterprise, corporate reward, employee incentive, educational);
   create, activate, reload, redeem (partial + full), expire.
   *Done when:* a digital gift card can be created, activated, partially redeemed twice, and its
   remaining balance is correct after both redemptions.
2. **`GiftCardPaymentMethod`** — registers WMPC Gift Card as a payment method inside the existing
   Payment Gateway Framework.
   *Done when:* an existing checkout flow (e.g. a subscription purchase) accepts a WMPC Gift Card
   as full or partial payment alongside an existing payment method, without a new checkout code
   path being written.
3. **Security layer** — PIN protection, fraud detection (extends existing Security Framework),
   duplicate-code prevention, real-time validation, anti-tampering, suspicious-activity detection,
   transaction monitoring feeding the existing Audit System.
4. **QR/Barcode support** — code generation and redemption-by-scan; NFC stubbed only, per spec's
   "future" marking.
5. **User features** — purchase, send, receive, redeem, balance/history view, scheduled delivery,
   saved recipients, personalized messages.
6. **Enterprise features** — bulk creation, employee rewards, customer loyalty programs,
   promotional/incentive campaigns, educational scholarships, sales bonuses, department spending
   limits.
7. **AI Payment Intelligence** — spending analysis, gift recommendations, fraud detection, usage
   and revenue forecasting, customer behavior analysis, loyalty/promotion optimization — all as
   agents extending `ExpertAgent`, registered into the existing AI Workforce.
8. **Admin dashboard** — cards issued/active/redeemed, outstanding balances, revenue, redemption
   rates, fraud alerts, regional usage, corporate account view.
9. **Enterprise integration pass** — confirm Wallet, Subscription, Marketplace, AI Marketplace,
   Creator Economy, Billing, CRM, Analytics, Accounting, BI, Workflow Engine, Security, and
   Governance all see gift card transactions through their existing interfaces, with no parallel
   data path introduced anywhere in steps 1–8.

## 79.3 Conventions Log — additions for `CONVENTIONS.md`

- **Payment methods register, they don't replace:** `GiftCardPaymentMethod` is a plugin into the
  existing Payment Gateway Framework's payment-method registry — this is now the required pattern
  for any future spec that introduces a new way to pay (crypto, mobile money, etc. if they come up
  later).
- **Gift card AI agents extend `ExpertAgent`:** third platform area (after Session 77's domain
  experts and Session 78's UI/UX agents) to standardize on the same agent base — confirms this is
  simply how every AI capability in WINDELS AI OS gets built now, not something scoped to any one
  session.
- **NFC treated as an explicit stub, not omitted:** where a spec marks a capability "(future)," add
  a named stub file rather than leaving it out entirely — keeps the eventual implementation's
  location decided now instead of debated later.
- **Fraud/security work extends, doesn't fork:** `FraudDetection.ts` and `TransactionMonitoring.ts`
  call into the existing Security Framework and Audit System rather than maintaining their own
  fraud-scoring logic — same non-duplication principle applied to security specifically.

## 79.4 Open Questions

1. **Physical card fulfillment:** the spec lists "Physical Gift Cards" as a supported type — does
   WINDELS AI OS need an actual print/ship fulfillment integration, or is "physical" scoped to
   record-keeping only (e.g. a physical card activated via a code that was mailed by a
   third-party)?
2. **Cross-currency gift cards:** Session 79 predates Session 80's currency engine — should gift
   card balances be single-currency at launch (matching org base currency) with multi-currency
   support deferred to after Session 80 lands, or built currency-aware from the start?
3. **Trading Edition:** consistent with prior sessions — does the stripped-down Trading Edition
   variant get gift cards at all, given it's a two-workforce sandbox?

# SESSION 80 — Global Multi-Currency & Intelligent Localization Payment Platform

> Depends on Session 79 landing first — this spec explicitly lists "WMPC Gift Card Platform" among
> the systems it extends, and payment localization includes adapting WMPC Gift Card specifically.

## 80.1 Database Schema Additions

New tables only, foreign-keyed into existing `organizations.id`, `users.id`, and Session 79's
`gift_cards` table where relevant.

`supported_currencies`, `exchange_rates`, `exchange_rate_history`, `exchange_rate_overrides`,
`user_currency_preferences`, `regional_pricing`, `promotional_pricing_by_region`,
`localized_receipts`, `regional_compliance_notices`, `currency_conversion_reconciliation`,
`currency_fraud_flags`

## 80.2 Build Steps

1. **`CurrencyIntelligenceEngine` + `LocalizationContext`** — detect/accept country, region,
   currency, language, time zone, number format, date format, tax region; single locale-state
   object every pricing surface reads from.
   *Done when:* one existing pricing display (e.g. a subscription page) renders in a
   user-selected currency using `LocalizationContext`, with no currency logic left in the
   component itself.
2. **Exchange Rate Provider** — live, cached, historical, enterprise-override, and offline-fallback
   rates from multiple providers, with scheduled sync through the existing Workflow Engine and
   rate validation.
3. **User currency preferences** — auto-detect, manual override, multiple saved currencies,
   instant switching, cross-device sync.
4. **Payment localization** — adapt each existing payment method (WMPC Gift Card from Session 79,
   cards, bank transfer, digital wallets, mobile money, local payment networks, crypto where
   enabled, enterprise invoicing) per country.
5. **Local payment experience** — currency symbol, decimal format, tax rules, regional payment
   instructions, localized receipts, country-specific compliance notices.
6. **Business & marketplace support** — org base currency, regional/country-specific/promotional
   pricing, revenue-by-currency views, multi-currency reports, conversion reconciliation.
7. **AI Payment Intelligence (currency)** — cost-effective payment-option recommendation,
   exchange-rate trend analysis, currency-fluctuation forecasting, international pricing
   optimization, unusual-payment-behavior detection, regional purchasing-trend monitoring — as
   `ExpertAgent`-based agents.
8. **Security & compliance** — exchange-rate validation, fraud detection, currency-manipulation
   protection, regional compliance, audit logging, transaction integrity, encryption — extending
   existing Security Framework and Audit System.
9. **Enterprise integration pass** — confirm Billing, Wallet, WMPC Gift Card, Subscription,
   Marketplace, AI Marketplace, Creator Economy, CRM, BI, Analytics, Accounting, Workflow Engine,
   Security, and Governance all resolve currency through `LocalizationContext`, with no second
   locale/currency computation path anywhere in the platform.

## 80.3 Conventions Log — additions for `CONVENTIONS.md`

- **Single locale-state pattern:** `LocalizationContext` is the one and only place currency/
  region/tax-region state is computed per request — no dashboard component, report, or agent
  computes its own currency logic. This is the multi-currency-specific instance of the
  registry-not-copy rule first established in Session 78.
- **Payment localization adapts, doesn't reimplement:** `PaymentMethodLocalizer` wraps each
  existing payment method (including Session 79's `GiftCardPaymentMethod`) rather than each
  payment method separately implementing its own currency handling.
- **Currency AI agents extend `ExpertAgent`:** fourth area of the platform (after Sessions 77, 78,
  79) to use the shared agent base — this pattern is now unambiguously the platform standard.
- **Fallback-first exchange rates:** offline fallback rates are a first-class part of
  `ExchangeRateProvider`, not an afterthought — matches the spec's explicit "resilience during
  connectivity issues" requirement, worth calling out since it affects the interface design (rate
  lookups must be able to return a stale-but-valid rate rather than erroring).

## 80.4 Open Questions

1. **Default currency set at launch:** the spec lists 14 named currencies (NGN, USD, GBP, CAD, EUR,
   JPY, CNY, INR, ZAR, GHS, KES, AED, SAR, AUD) plus "support all internationally recognized
   currencies" — confirm whether launch scope is the 14 named currencies with the full ISO 4217
   list added incrementally, or all supported from day one.
2. **Exchange rate provider(s):** spec requires multi-provider support but doesn't name providers —
   need your preferred rate source(s) (e.g. a specific FX data API) before `ExchangeRateProvider`
   can be implemented against a real API rather than a mocked one.
3. **Crypto payment scope:** listed as "where enabled" — confirm whether crypto payment
   localization is in scope for this session or genuinely deferred until a future crypto-specific
   spec exists.
